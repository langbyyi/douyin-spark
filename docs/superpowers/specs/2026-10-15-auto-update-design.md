# 跨环境程序自动更新设计

日期：2026-10-15

状态：用户授权自主决定后已实现；验证结果见 `docs/auto-update-validation.md`。

## 目标与已确认需求

- 程序自动检查更新，用户在控制面板点击后更新并重启；不定时静默安装。
- 支持 Windows、macOS、Linux 原生 Python 部署，以及可运行现有 Compose 服务的 Docker 环境。
- 保留配置、代理与推送凭据、面板密码、抖音登录状态、发送账本和每日计划。
- 更新失败时尽可能恢复旧程序；不得将恢复失败显示为成功。
- 此处更新指程序升级，不是刷新好友或火花数据。

## 当前项目约束

- 当前通过 Git 克隆部署，README 的更新方式为手动拉取、安装并重启。
- `pyproject.toml` 与 `dyspark.__version__` 当前均为 `0.1.0`，因此仅比较版本号无法识别代码更新；首版按固定 Git 上游提交检查。
- GUI 使用 Starlette / uvicorn，已有密码会话及写操作令牌验证。
- GUI、MCP 和 CLI 共用数据目录；维护状态需要在进程之间生效。
- Docker 将源码复制进镜像，容器内没有宿主机仓库及容器管理权限。
- 现有 Docker 有 `local`、`spark`、`mcp` 三种服务；更新仅重启选定的 GUI 服务，不启动其他服务。
- 工作区存在用户未提交的改动，实现时不得覆盖、提交或清理这些改动。

## 路径比较与选择

| 路径 | 优点 | 代价或限制 |
| --- | --- | --- |
| 宿主机管理器监督服务（采用） | 能在程序退出后继续更新和恢复；原生与 Docker 共享更新协议 | 需一次性切换为管理器启动；Docker 宿主机增加 Python 3.11+ 前置条件 |
| GUI 内直接更新自身 | 原生接入简单 | 程序退出后失去监督；无法从普通 Docker 容器管理宿主服务 |
| Docker 容器访问宿主 Docker socket | 可从容器管理镜像 | 扩大面板服务权限，且仍不能统一原生部署流程 |

采用独立管理器与可切换的程序目录／镜像。既有手动启动方式继续可用，但未由管理器启动时仅提供检查与明确的启用说明，不能显示可用的一键更新按钮。

## 用户流程

1. 启用时运行一次对应部署环境的管理器启动命令；沿用原配置、数据路径、监听地址、端口、浏览器选择和安装组件。
2. 设置页新增“程序更新”，显示当前提交、可用提交、最近检查时间及管理器是否就绪。
3. 管理器启动后检查一次，之后每 6 小时检查；页面提供“检查更新”。网络失败不影响发送或每日计划，并显示错误及上次成功结果的时间。
4. 有更新时显示提交摘要及“更新并重启”；用户确认短暂中断后创建唯一更新请求。
5. 正在登录、发送、检查或拉取会话，或任务状态待核对时，拒绝开始更新并说明原因，用户稍后重试。
6. 页面显示准备、安装／构建、重启、验证、完成或失败状态；重启后重新加载页面并要求重新登录。

不增加定时无人值守安装、任意分支切换、自动恢复业务数据或公网更新管理端口。

## 模块与信任边界

- **更新管理器**：通过宿主 Python 标准库执行 Git、虚拟环境、pip 或 Docker Compose；持有单实例锁，监督它启动的原生子进程或选定 Compose 服务。
- **更新后端**：负责展示状态、校验请求、阻止并发更新、参与业务维护锁。GUI 沿用现有认证及 `X-Spark-Token`，不开放匿名更新接口。
- **文件协议**：数据目录的 `updater/` 仅保存请求、心跳和公开进度；宿主源码目录 `.spark-updater/` 保存权威事务、所有权、版本程序和 Compose 配置，禁止挂载给容器。文件原子替换并限制权限。请求只允许请求编号和已验证的目标提交，不接受命令、安装地址、任意路径或服务名。
- **原生适配器**：安装并启动新程序，保留原程序及解释器供恢复。
- **Docker 适配器**：在宿主构建独立镜像标签，通过 Compose 覆盖文件切换所管理服务，保留旧镜像标签供恢复；不挂载 Docker socket 给 GUI。
- **设置页组件**：使用现有样式和 API 辅助函数，按后台状态显示按钮与结果；用文本节点展示远端提交信息。

更新源固定为本仓库的官方上游，按启用时确定的上游分支检查提交，支持官方仓库的 HTTPS 与 SSH 地址形式。不得直接执行面板请求提供的仓库、分支或 shell 文本。目标必须为当前提交的后续提交；分叉、回退或无法确定关系时停止并说明原因。

## 更新事务

1. 校验管理器身份、部署能力、目标提交、上游关系、剩余更新状态与源码工作区。发现本地源码变更或未跟踪源码时停止；被 Git 忽略的用户配置与数据不构成阻塞。
2. 从已验证提交导出独立版本目录，避免修改用户源码工作区。目录只写入管理器专有状态区。
3. 原生环境创建独立虚拟环境并安装所需组件；Docker 构建目标镜像。失败时清楚记录阶段，旧服务继续运行。
4. 取得跨进程维护锁，再检查所有任务与数据锁；维护期间拒绝新 GUI、MCP、CLI 及调度任务，并暂停相关配置修改。存在活动任务时不强制终止。
5. 记录旧程序／镜像、启动参数及请求编号，正常停止受管理服务，切换到目标程序并启动。
6. 验证新服务就绪且运行的确为目标提交，再持久化当前版本指针并完成事务。健康检查不得发送消息或打开抖音浏览器；验证期间调度保持暂停。
7. 若启动或验证失败，切换回记录的旧程序／镜像，重新启动并验证，结果报告“更新失败，已恢复旧版”或“恢复失败，需要处理”。
8. 在成功运行目标版或确认旧版恢复后解除维护状态。启动时检测未完成事务；遇到未知状态先核对实际运行版本，禁止猜测成功或重复启动服务。

不在更新中删除、覆盖或回滚配置和业务数据。首版不执行数据库或业务数据格式迁移；涉及不可逆数据迁移的未来版本需单独设计，不承诺自动回滚。

## 各环境要求

| 环境 | 一键更新要求 | 验证方式 |
| --- | --- | --- |
| Windows 原生 | Git、Python 3.11+、管理器启动；后台辅助进程隐藏窗口 | 本机进程启动、停止、更新和恢复测试 |
| Linux / macOS 原生 | Git、Python 3.11+、管理器启动 | 同一原生适配器；对应系统实际运行验证 |
| Docker 本机或服务器 | 宿主 Git、Python 3.11+、Docker Compose；管理器具备已有 Docker 操作权限 | 真实镜像构建、容器替换和旧镜像恢复测试 |
| 无源码仓库的 wheel / 受外部系统管理的部署 | 检查与能力提示；先以文档方式接入管理器 | 不误报支持；不直接终止未知进程或外部服务 |

Docker 服务仅支持其现有网络及平台要求；增加更新功能不使 Linux host 网络部署自动兼容其他平台。外部 systemd、容器编排或服务管理器必须按文档选择唯一服务所有者，避免两个管理器同时重启同一服务。

## 测试与交付标准

- 使用本地临时 Git 远端模拟有更新、无更新、分叉、拉取失败、脏工作区、含空格或中文路径；不修改真实上游和当前工作区。
- 原生更新测试验证真实隔离目录、配置和登录文件保留、健康验证、更新失败恢复及中断恢复。
- 并发测试覆盖重复点击、两个管理器、任务启动与进入维护的竞态，以及 GUI / MCP / CLI 共用数据目录。
- GUI API 测试覆盖未登录、缺少令牌、未知提交、过期管理器心跳和重复请求；设置页验证进度、失败及重启后的登录流程。
- Docker 适配器先用可控命令边界验证调用参数与失败分支，再在具备 Docker 的环境做真实构建与恢复验证。
- 执行现有测试、Ruff、格式检查及 wheel 构建；记录无法实际运行的平台，不能以模拟测试代替跨平台实测结论。
- 补充 README、原生启动与 Docker 部署文档，明确首次接入步骤、Python 前置条件、日志位置和失败恢复方式。
